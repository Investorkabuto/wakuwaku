# 06. Webアプリ先行で始める場合の課題

> ステータス: ドラフト v0.1 / 2026-10-16
> 前提: 最初の10人規模のテストを、ストアアプリではなくWebアプリ（PWA）で行う

## 1. Web先行のメリット

- ストアの審査がなく、すぐに修正を反映できる。Apple Developer や macOS でのビルドが当面いらない
- テスターはURLを開くだけで使える。家族がLINEでリンクを送れば参加できる
- Goサーバー、DB、Firebase Auth はそのまま使える。Connect RPC はブラウザにも対応している

## 2. 課題一覧

### 【重大】A. 服薬リマインド通知

| 問題 | 内容 |
|---|---|
| オフラインで鳴らせない | Webには「端末で時刻を予約して通知する」標準の仕組みがない。**通知は必ずサーバーからのプッシュになる**（MED-03「オフラインでも鳴る」は実現できない） |
| iPhoneの制約 | iOS の Safari でWebプッシュを受け取るには、**「ホーム画面に追加」したPWAとして起動し、通知を許可する**必要がある（iOS 16.4以降）。高齢者が一人で行うのは難しい |
| 届かないことがある | ブラウザやOSの省電力機能、通知の許可の取り消し、ホーム画面アイコンの削除などで、気づかないうちに届かなくなる |

**対策**
- 通知の手段を複数にする：**Webプッシュ＋LINE（Messaging API）＋メール**。日本の高齢者にはLINEがいちばん確実に届く。
  - LINE Notify は2025年3月に終了済み。公式アカウントとMessaging APIを使う。月の送信数によっては有料プランが必要（料金は要確認）
- 初期設定は家族が代わりに行う：ホーム画面への追加と通知許可を画面付きの手順で案内する。「テスト通知」ボタンで届くことを確認する
- サーバー側で「通知を送れたか・開かれたか」を記録し、届いていない人を家族と運営が把握できるようにする

### 【重大】B. 歩数・ヘルスケア連携ができない

- ブラウザから HealthKit／Health Connect のデータは読めない。**歩数の自動取得（EXE-01）はできない**
- 対策：Web版では運動は「やった」の手動チェック（体操・散歩）だけにし、歩数連携はネイティブアプリで対応する

### 【重大】C. 3D表示の重さ（3Dと低価格スマホのブラウザ）

| 問題 | 内容 |
|---|---|
| 初回読み込み | Flutter Web は描画エンジン本体だけで数MBあり、そこに3Dアセットも加わる。高齢者の端末や回線では、表示まで長く待たされる |
| 性能・メモリ | 古めのAndroidのブラウザではWebGLが遅い。iOS Safari はメモリ上限を超えるとタブごと再読み込みされる |
| flutter_scene | Web版（WebGL2）にも対応はしているが、プレビュー版で開発版チャネルが必要（ADR-001のリスクがそのまま残る） |

**対策**：Web版の最初のテストでは、3Dは「眺めて触れる農園」程度の軽い表現にする。服薬・見守り・交流の仕組みの検証を優先する。3D画面は後から読み込み、通信量を抑えるモードでは静止画で代わりに表示する。

### D. 技術スタックの選択（Flutter Web か Web 専用か）

| | Flutter Web | Web専用（React など＋three.js） |
|---|---|---|
| 将来のネイティブ版でのコード再利用 | ◎ そのまま流用できる | × ネイティブ版は作り直し |
| 初回の読み込み・軽さ | △ 重い | ◎ 軽い |
| アクセシビリティ | △ 画面全体を絵として描くため、ブラウザの拡大や読み上げとの相性に注意が必要 | ◎ 通常のWebページ（HTML）なので標準の仕組みが使える |
| 3Dの成熟度 | △ flutter_scene（プレビュー版） | ◎ three.js は成熟している |

**推奨：Flutter Web**。最終的にはFlutterのネイティブアプリにする前提なので、作り直しを避ける。ただし以下の点を確認し、問題があればWeb専用への切り替えを判断する。
- 文字の拡大（OSやブラウザの設定）と読み上げ（VoiceOver／TalkBack）が実用的に動くこと
- 中位Android端末で、初回表示がおおむね5秒以内であること

### E. データの保存とオフライン対応

- iOS の Safari は、**7日間開かれなかったサイトのデータを自動で消す**ことがある（ホーム画面に追加したPWAは対象外）。→ 端末側のデータは一時的な保存にとどめ、**正しいデータは常にサーバー側に置く**
- オフラインでの記録は、ブラウザ内のデータベース（IndexedDB または WebAssembly 版のSQLite（drift））に一時的に保存し、つながったときにサーバーへ送る（「のんだ」の記録は追記型なので、送信が重なっても重複しない）

### F. 高齢者の使いやすさ（ブラウザならではの問題）

- アドレスバーや戻るボタンでタブを閉じたり、ページから離れたりしやすい → PWAとして全画面で起動し、画面内の戻るボタンを統一する
- ログイン状態が切れると操作できなくなる → ログインの有効期間を長くする（リフレッシュトークン）。再ログインが必要になったら家族に知らせる
- 読み上げは Web Speech API を使うが、日本語の音声の質は端末によって違う → 字幕と大きな文字を基本にする
- 音の自動再生は制限される → 最初の操作のタイミングで音声の再生を許可してもらう

### G. セキュリティ

- 健康情報をブラウザで扱う → XSS対策（CSP）、ログイン情報（トークン）の保存方法、家族で共有している端末で使うときの注意喚起
- Firebase App Check（reCAPTCHA Enterprise）でボット対策をする
- APIへのアクセス元の制限（CORS）と、レート制限（同じ人からの連続リクエストの制限）

### H. 要件への影響（02_requirements.md の調整）

| 要件 | Web版での扱い |
|---|---|
| MED-03 オフラインでも鳴る通知 | **サーバー送信の通知に変更**（Webプッシュ／LINE／メール） |
| EXE-01 歩数の自動取得 | **Web版では対象外**（手動チェック） |
| ACC-02 QRコードによる代行設定 | **招待リンク（LINEで送る）**＋家族による代行設定に変更 |
| NTF-01 端末内通知 | ネイティブ版で対応 |
| GAM（3D農園） | 軽い表現で開始。本格的な3Dは技術検証後に判断 |

## 3. Web版MVPの構成案

```
[ブラウザ / PWA]  Flutter Web（ホーム画面に追加して使う）
      │  Connect RPC (HTTPS)
      ▼
[Firebase Hosting] 静的ファイルの配信（無料枠）
[Cloud Run]        Go API
[Cloud SQL]        PostgreSQL（東京）
[Cloud Scheduler]  服薬リマインドの送信・見守り判定 ← Web版ではリマインドもサーバーから送る
[通知]             FCM Webプッシュ / LINE Messaging API / メール
```

費用は 05_test_environment.md の構成に、LINE Messaging API の料金（送信数による）が加わる程度。
