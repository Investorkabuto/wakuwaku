# 04. 技術選定の検討（ADR）

> ステータス: ドラフト v0.1 / 2026-10-16

## 前提（決定事項）

| 項目 | 決定 |
|---|---|
| 表現 | **3D** |
| アート制作 | **自社**（開発担当がコードで制作） |
| 開発体制 | **開発はすべてAI（Claude）が担当**。期間は問わない |
| B2B展開 | 未定（拡張できる構造にしておく） |

この前提から、技術選定では次の3点を重視する。

1. **コード／テキストだけで作業が完結すること**：GUIエディタがないと作れない技術は、AIが開発するうえで大きな足かせになる
2. **高齢者向けUIの品質**：文字の拡大、読み上げ、OSのアクセシビリティ機能。これらはFlutterが強く、ゲームエンジンは弱い
3. **長期的な拡張性**：リアルタイム交流、法人向け、医療連携

## ADR-001: 3D描画の方式

### 基本構成：Flutterのアプリの中に3Dの画面を埋め込む

タスク・服薬・見守り・設定など**3D以外の画面はすべてFlutter**で作る。農園や村の**3D画面だけを描画エンジンに任せる**。こうすることで、高齢者向けUIの品質と3D表現を両立させる。

3D画面の上に重なるボタンや吹き出しもFlutterで描く。そのためにアプリと3Dエンジンの間に「GameBridge」という接続層を設け、エンジンを入れ替えられるようにしておく。

### 選択肢

| | A. flutter_scene（Dart製の3D） | B. Godot 4.6+（LibGodotで埋め込み） | C. Unity 6（Unity as a Library） |
|---|---|---|---|
| 言語 | Dart（アプリと同じ） | GDScript / C# | C# |
| Flutterとの統合 | ◎ 同じ画面ツリーに入り、ボタンなどを重ねやすい | △ ネイティブの接続コードを自作する必要あり（Flutter用の公式な仕組みはまだ初期段階） | ○ 有志のプラグインあり（Unity 6への対応は派生版。画面遷移で固まる不具合の報告あり） |
| 成熟度 | △ バージョン1.0前のプレビュー版。Flutterの開発版チャネルが必要 | ○ エンジン自体は成熟。埋め込み機能はGodot 4.6で入ったばかり | ◎ 製品としての実績は最も多い |
| AIによる開発のしやすさ | ◎ すべてコードで書ける | ◎ シーンもテキスト形式で、エディタなしでビルドできる | △ エディタ前提。シーンやプレハブの編集、CIでのライセンス認証が重い |
| アプリサイズ・メモリ | ◎ 小さい | ○ | △ 大きい |
| ライセンス | BSD | MIT（無料） | 売上の規模に応じて有償 |
| 主なリスク | 仕様変更（破壊的変更）、ストア公開時の安定性 | Flutter連携を自作・保守する手間 | エディタ依存、プラグイン保守の不安 |

### 推奨

**第1候補は A. flutter_scene、第2候補は B. Godot。C. Unityは採用しない。**

- 期間を問わない前提なので、今はプレビュー版の flutter_scene でも、正式公開までに安定する見込みに賭けられる。言語が1つで済み、統合の手間がないことが、AI1人の開発では最も効く。
- ただし、Phase 0で**技術検証用の試作**を行い、以下の基準を満たせなければ Godot に切り替える。
  - 中位〜下位のAndroid端末（例：3年前の中位機種）で、農園画面が30fps以上
  - 3D画面とFlutterのボタンを重ねても、操作や読み上げに問題がない
  - 安定版チャネル、または固定した開発版で、ストアに公開できるビルドが作れる
- GameBridge 層を挟むので、切り替えても3D以外の画面には影響しない。

## ADR-002: 3Dアートの制作方法（自社制作）

- **表現スタイル**：ローポリ（少ない面数）のアニメ調。手描き風の質感を、少ない色とトゥーンシェーダーで出す。動物系のキャラクターや丸みのある作物にすると、ローポリでも可愛く見え、端末への負荷も小さい。
- **作り方**：**Blender の Python スクリプトで、モデルをコードから作る**。画面なしでBlenderを動かし、glTF形式で書き出す。
  - 作物・家具・地形：形のパラメータを変えて、いろいろな種類を作る
  - キャラクター：共通の骨格に、パーツ（耳・しっぽ・服）を組み合わせる
  - アニメーション：歩く・水やり・喜ぶなどの動きもスクリプトで作る
- **作業の流れ**：スクリプトをGitで管理し、CIで書き出しから軽量化、アプリへの組み込みまで行う。見た目の確認は自動で撮ったスクリーンショットで行う。
- **限界と補い方**：手作業で作る作品に比べると、表現の上限は低い。必要になったら、CC0（自由に使える）素材の利用や一部の外注も選べるようにしておく。

## ADR-003: サーバー構成

### 選択肢

| | Dart（Serverpod） | **Go** | TypeScript（NestJS） | Kotlin（Spring） | Nakama（ゲームサーバー製品）＋独自拡張 |
|---|---|---|---|---|---|
| アプリとのコード共有 | ◎ 同じ言語 | △ スキーマから自動生成 | △ 同左 | △ 同左 | △ |
| 処理性能・同時接続 | ○ | ◎ | ○ | ○ | ◎ |
| リアルタイム同時訪問への拡張 | ○ ストリーミング機能あり | ◎ | ○（Colyseus） | ○ | ◎ 機能として最初から持っている |
| 周辺ライブラリ（医療連携など） | △ 少ない | ○ | ◎ | ◎ | △ |
| 運用コスト（Cloud Run） | ○ | ◎ 単一ファイル・起動が速い | ○ | △ 起動が遅め | △ 常時起動が必要 |
| 3Dエンジンを変えたときの影響 | エンジンがDart以外になると共有の利点が消える | 影響なし | 影響なし | 影響なし | 影響なし |
| 法人向けの信頼性 | △ | ◎ | ○ | ◎ | △ |

### 推奨：Go の「モジュラーモノリス」＋スキーマ先行設計

サーバーは最初は1つのアプリとして作り、中を機能ごとのモジュールに分ける（モジュラーモノリス）。API仕様は先にスキーマで定義し、そこからコードを生成する。

- **API**：Connect RPC（Protocol Buffers）。スキーマから、サーバー用のGoコードとアプリ用のDartコードを両方生成する。どの3Dエンジンを選んでも同じ仕様をそのまま使える。
- **モジュール分割**：`identity` / `care`（服薬・タスク・見守り）/ `game`（農園・経済）/ `social`（家族・交流）/ `admin` に分ける。
  - 将来、法人向けや医療連携が必要になったら、`care` だけを別サービスとして切り出す。健康データの区画を分ける・監査を強める、といった対応をしやすくするため。
- **リアルタイム同時訪問（Phase 3）**：同じGoで `realtime` サービスを追加する（WebSocket＋Redisでメッセージを配信）。そこまでの規模が見込めた時点で、Nakama の導入も改めて検討する。
- **ゲームロジックの整合**：作物の成長計算や報酬計算はサーバーの判定を正とする。アプリ側は、オフラインでも動くよう同じ計算をDartで持つ。両方の実装が同じ結果になることは、**共通のテストケース（JSONのゴールデンデータ）**で、GoとDartの両方からテストして保証する。

### Dart（Serverpod）を選ばない理由

3Dエンジンが Dart（flutter_scene）に決まれば、言語を共有できる利点は確かに大きい。しかしADR-001の検証結果によってはGodotに切り替える可能性がある。また、リアルタイム処理・法人向け・医療連携まで見据えると、エコシステムと運用面で Go のほうが優位と判断した。

## 次のアクション（Phase 0の技術検証）

1. flutter_scene で最小の試作を作る：畑4マス・キャラクターの移動・水やりのアニメーション・Flutterボタンの重ね表示
2. Blenderスクリプトでの制作の流れを確認する：作物1種類（3段階の成長）と、キャラクター1体（歩くアニメーション）
3. Go＋Connect RPC の土台を作る：認証、服薬記録の同期、Dartクライアントの自動生成
4. 実機で性能を測り、ADR-001を確定する

## ADR-004: 初期インフラ（少人数運用）— Firebase ＋ Go のハイブリッド

### 決定
**Firebase は「周辺機能」に使い、主要データとビジネスロジックは Go API ＋ PostgreSQL に置く。**

| 領域 | 採用 | 理由 |
|---|---|---|
| 認証 | **Firebase Authentication** | SMS・Apple・Googleのログインをすぐに作れる。Go側では `firebase-admin-go` でログイン情報（IDトークン）を検証する |
| プッシュ通知 | **FCM** | 無料。Goの Admin SDK から送信できる |
| クラッシュ・分析 | **Crashlytics / Analytics** | 運用の手間がかからない |
| リモート設定 | **Remote Config** | 段階リリース、機能の切り替え |
| 不正対策 | **App Check** | 正規のアプリからの通信だけをAPIで受け付ける |
| 画像・アセット | **Cloud Storage for Firebase** | 薬の写真（署名付きURLで配布）、3Dアセットの追加ダウンロード |
| API | **Go on Cloud Run**（東京リージョン、アクセスがなければ0台まで縮小） | 少人数の段階ではほぼ無料枠で動き、規模が大きくなればそのまま台数を増やせる |
| DB | **PostgreSQL（Cloud SQL の最小構成）** | 家族関係・同意・見守り判定はリレーショナルなデータ構造に合う |
| 定期ジョブ | **Cloud Scheduler → Cloud Run** | 見守り判定（5分ごと・1時間ごと）。常時起動のサーバーが不要 |

### Firestore を主要DBにしない理由
- 服薬などの健康情報は「本人が同意した項目だけを、同意した家族に見せる」という細かな権限管理が必要になる。これをアプリからDBへの直接アクセスとセキュリティルールで守るのは、ルールが複雑になってミスが起きやすい。
- 「予定時刻を過ぎても記録がない服薬」の検索や、家族グループをまたぐ集計は、Firestoreが苦手な処理。
- ゲーム内の通貨や報酬はサーバーの判定を正とする必要があり、結局APIサーバーを経由することになる。
- オフライン対応は端末内のDB（drift）と同期の仕組みで行うので、Firestoreのオフライン機能に頼る必要がない。

### 注意点
- SMSでの電話番号ログインはSMSの送信ごとに課金される。Apple・Googleログインを優先し、SMSは高齢者の代行設定などで必要な場面に絞る。
- Firebase Auth のデータは国外で保管される可能性がある。プライバシーポリシーで、外部事業者への取り扱い委託と保管場所を明記する。健康情報は Firebase に置かず、東京リージョンのPostgreSQLだけに保存する。
- 規模が大きくなったときは、DBの性能を上げる（Cloud SQL の上位構成やAlloyDB）、Redisを追加する、`care` モジュールを別サービスに切り出す、の順に対応する。Firebase の部分はそのまま使い続けられる。

## ADR-005: Web版を先に作る ― Web専用技術（SvelteKit + three.js）＋Webプッシュ

### 決定
最初のテスト（10人規模）は **ホーム画面に追加して使うWebアプリ（PWA）** で行う。ADR-001（Flutter＋flutter_scene）は、ネイティブアプリを作る段階で改めて判断する。

| 領域 | 採用 | 理由 |
|---|---|---|
| UIフレームワーク | **Svelte 5 + SvelteKit**（静的ファイルとして書き出し、ブラウザ側だけで動くSPA） | 軽さを最優先する。ランタイムが小さく、初回表示が速い |
| 言語 | TypeScript | |
| 3D | **three.js**（後から読み込む） | 成熟していて軽い。農園画面に入ったときだけ読み込む |
| API | Connect RPC（`@connectrpc/connect-web`、protobuf から TypeScript のコードを生成） | Goサーバーと同じ定義を使う |
| 通知 | **Webプッシュ（VAPID方式で、Goから直接送信）** ＋ 予備としてメール | 無料。FCMを経由しないので仕組みが単純 |
| 配信 | Firebase Hosting | 無料枠で足り、Firebase Auth と同じプロジェクトで管理できる |
| 認証 | Firebase Auth（Web SDK） | ADR-004 のとおり |

### 補足
- 服薬リマインドは**サーバーから送る**（Cloud Scheduler で毎分起動し、送るべき通知を送信する）。オフラインでは鳴らない点を利用者に説明する。
- 通知が届かなくなった人を検知する：送信に失敗したら、その宛先を無効にする。服薬記録が一定期間なければ、本人と家族に知らせる。
- やさしいモードでは、ダブルタップでの拡大、画面を引っ張っての再読み込み、長押しメニューを無効にする。画面内に戻るボタンを必ず置く。iPhoneでは振動が使えないため、押した感触は見た目の変化と音で伝える。
- ネイティブアプリにする時の選択肢：(a) Capacitor でWeb版をそのままアプリに包む（端末内通知・HealthKit 連携をプラグインで追加でき、画面を再利用できる）、(b) Flutter で作り直す。テスト結果を見て決める。
